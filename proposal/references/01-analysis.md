# 1. 분석 — RFP·요구사항 분석 (관문 A)

## 목표

제안서의 모든 판단이 기대는 기초 자료를 만든다. 산출물 세 가지:

1. `01_분석/분석보고서.md` — RFP 상세 분석
2. `01_분석/요구사항매트릭스.xlsx` — 요구사항 한 건씩 분석
3. `01_분석/용어사전.md` — 업무·IT 배경이 없는 사람을 위한 뜻풀이

## 읽는 방법 (검증된 요령)

1. **추출부터 한다.**
   ```
   python <스킬>/scripts/extract_inputs.py <RFP 폴더 또는 파일> 제안작업/01_분석/_추출
   ```
   - PDF는 페이지별 텍스트(`*_pages.txt`)와, **글자가 적은 페이지의 이미지**(`*_p{번호}.png`)를 만든다.
   - 엑셀은 시트별 텍스트 덤프와 내장 이미지를 만든다.
2. **텍스트를 끝까지 읽는다.** 길면 나눠 읽는다. 요약만 보고 판단하지 않는다.
3. **이미지 페이지를 직접 본다.** 시스템 구성도, 일정 간트, 인터페이스 표, 화면 시안처럼 핵심 정보가 이미지로만 들어 있는 경우가 많다.
4. **요구사항 엑셀은 행 단위로 전수 확인한다.**
   - 양식에 남은 **샘플 행**(다른 업무의 예시 행)을 걸러 낸다.
   - 빈 To-be, 미완성 문장, 작성 메모(초안 흔적) 같은 문서 결함을 기록한다.
   - 시트별 "1차 오픈" 같은 표기를 집계한다. 발주처의 단계 구상과 모순이 드러난다.
   - 행마다 작성 형식이 갑자기 달라지는 구간은 성숙도가 낮을 가능성이 크다(범위 확장 위험).

## 반드시 찾을 것

- **문서 간 불일치**: 본문 vs 간트, 본문 vs 요구사항 엑셀, 시스템 구성도 vs 엑셀, IA(화면 구조) vs 요구사항, 별첨 번호 오류, 같은 개념의 다른 용어(예: 희망가/최소입찰가/즉시체결가).
- **과제·범위 분류 차이**: 과제별 공수 제출이 필수인데 과제 분류가 문서마다 다르면 반드시 질의로 올린다.
- **요구와 규정의 충돌**: 예) AI로 공수를 줄이라는 요구 vs 생성형 AI 사용 금지 보안 규정, VDI 개발 의무 vs iOS 빌드(Mac 필요).
- **상한 없는 책임 조항**: 예) "범위 외 취약점도 조치", 무제한 요구 변경 수용.
- **발주처 결정에 의존하는 항목**: "추후 안내", "당사 검토 후 안내" → 일정 리스크.
- **발주처의 숨은 의도**: 수치로 드러난 문제(전환율, 오류 건수, 지원 종료 일정)와 사업 목표의 연결.

## 표기 규칙

분석 문서의 판단에는 표시를 붙인다.
- **[사실]** RFP·엑셀에 적힌 내용 (쪽수·요구사항 번호 병기)
- **[해석]** 분석자 판단
- **[가정]** 확인 전 전제
- **[질의]** 발주처 확인 필요 (질의서 번호 병기)

## 분석보고서 목차

```
0. 핵심 요약 (사업 성격, 규모, 기간, 평가, 최대 리스크 3~4개, 핵심 판단, 즉시 할 일)
1. 사업 개요 (용역명, 기간, 계약 방식, 평가 비율, 행정 일정, 제출처)
2. 추진 배경과 발주처 의도 (RFP가 밝힌 배경, 수치로 드러난 문제, 숨은 의도)
3. 현행 시스템 환경 (기술 스택·노후도 표, 인프라, 구성도 해석)
4. 사업 범위 구조와 요구사항 통계 (과제 정의, 시트별·기능군별 통계, 분류 불일치)
5. 과제별 상세 분석 (항목마다 현황·요구·쟁점·권장 접근)
6. 인터페이스 분석 (내부·외부, 책임 범위)
7. 일정·단계별 오픈 전략 (간트 판독, 불일치, 부하 분석, 권장 일정안)
8. 인력·조직 요건
9. 보안·수행환경 제약
10. AI 요건 (있을 때)
11. 사업관리·산출물 요건
12. 평가·제출 요건과 체크리스트
13. 규모 추정(초벌) — 가정 명시, 가격 산정용 아님을 밝힌다
14. 리스크 레지스터 (ID, 리스크, 가능성, 영향, 대응)
15. 불일치·누락 목록과 질의서 초안
16. 제안 전략 초안 (Win theme 후보, 차별화, 가격 관점, 발표 구성)
```

규모 추정 주의: 총 M/M ÷ 기간 = 평균 인원일 뿐이다. 실제 투입은 피크가 있는 곡선이고, 부분 투입 인력 때문에 명단 인원은 더 많다. 이를 구분해 적는다.

## 요구사항 매트릭스(엑셀)

시트 1 "요구사항 분석 매트릭스" 열:
`시트 | 과제 | No | 시스템 | L1 | L2 | L3 | 기능명 | 기능군 | 신규/변경 | 1차 오픈 | 난이도(상/중상/중/하) | 분석 메모·질의 포인트 | To-be 원문(앞부분)`

시트 2 "집계": 과제·기능군별 건수, 1차 오픈 수, 신규/변경 수. 가능하면 수식(COUNTIFS)으로 만든다.

- 난이도는 "초벌"임을 열 이름에 밝힌다.
- 질의 포인트가 있는 행은 빨간 글씨로 강조한다.
- 머리글 고정, 자동 필터, 열 너비 조정.

## 용어사전

- 대상: 업무·IT 배경이 없는 사람.
- 항목 형식: **용어(원어)** 다음 줄에 뜻풀이, 그다음 줄에 "이 사업에서는: …(요구사항 번호)". "쉽게 말하면:" 같은 머리말은 쓰지 않는다.
- 장 구성 예: 사업·계약 / 프로젝트 관리 / 등장 시스템 이름 / 업무 도메인 용어 / 회원·계정 / 정산·결제 / 화면·디자인 / 개발 기본 / 구체적 기술 이름 / 데이터 / 연동·외부 업체 / 보안·개인정보 / 인프라·운영 / **헷갈리는 용어 비교표** / **약어표**.
- RFP와 요구사항에 실제로 나온 용어만 넣는다.

## 관문 A 보고

- 핵심 요약 5줄 이내
- 불일치·리스크 상위 5개
- 사용자가 결정할 것(예: 과제별 공수 기준, 제안 일정안 방향)
- 다음 단계: 질의서(설명회·질의 마감이 가까우면 먼저) 또는 전략
