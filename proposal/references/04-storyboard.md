# 4. 원고 — 장표별 스토리보드 (관문 C)

## 산출물

- `04_원고/00_전체구성.md` — 장표 번호 목록(장-절-장표, 제목, 도식 유형, 담당, 상태)
- `04_원고/{장}장_{제목}.md` — 장별 원고. 담당자가 나눠 고칠 수 있게 장마다 파일을 나눈다.

## 장표 형식

`review_storyboard.py`가 읽을 수 있게 **이 형식을 정확히 지킨다.** 양식은 `assets/storyboard-template.md`.

```markdown
### [2-3-1] 무중단 인프라 전환 전략

- 헤드메시지: 경매가 없는 시간대의 일괄 전환과 2회 리허설로 실시간 경매 중단 없이 Java 17 전환을 완료합니다.
- 본문:
  - Hazelcast 3→5 클러스터 비호환 → 서버 일괄 전환, 딜러 CS 클라이언트 강제 업데이트
  - 모의경매 환경 리허설 2회, 롤백 절차 사전 검증
  - 전환 전후 응답시간·TPS 비교 검증
- 슬로건: 미리 검증하는 리허설, 경매 없는 시간의 전환
- 키워드: Rehearsal · Cut-over · Rollback · Monitoring
- 도식: R2 일정+기준 | KPI 띠(중단 0분·리허설 2회·롤백 30분), 컷오버 타임라인 D-14 ~ D+7, 오른쪽 롤백 기준 4개
- 요약 바: (선택) 장표 결론 3~4칸 — 숫자 제목 + 한 줄
- 근거: RFP p8, 요구사항 1-1 #1(Hazelcast 3.12.2 → 5.6.x, 사용 파일 35개)
- 대응: REQ-1-1-001, TOC-2-9
- 담당: 홍길동
- 상태: 초안
```

필드 설명:
- **헤드메시지**: 이 장표에서 평가위원이 기억할 **완결된 주장 문장** 1~2줄. 주어와 약속이 분명해야 한다. 명사형 제목의 반복이 아니다.
- **본문**: 개조식. 명사형("~구축", "~확보") 또는 "~함" 종결. 한 장표에 3~6개. 한 항목은 한 줄 반 이내.
- **슬로건**(선택): 명사형 대구 한 줄, 명사로 끝낸다("~다" 금지, `style-guide.md` 슬로건). 주요 장표(장 첫 장표, 전략, 결론)에는 넣는다.
- **키워드**(선택): 슬로건의 핵심 개념 3~4개 영문 명사.
- **요약 바**(선택): 장표 결론을 숫자·짧은 제목 3~4칸으로.
- **도식**: `유형 | 구성 요소와 강조점`. 회사 스타일 레시피(R1~R8, `visual-patterns.md` 6.1)나 패턴 이름을 쓴다. 유형은 `references/visual-patterns.md`의 이름을 쓴다. **"없음"은 표지·목차·간지 외에는 쓰지 않는다.**
- **근거**: RFP 쪽수, 요구사항 번호, 발주처 수치, 회사 실적 출처. 없으면 [근거 필요].
- **대응**: `추적대상.csv`의 키. 쉼표로 여러 개.
- **담당**, **상태**(초안/검토/완료).

## 일반론 방지 규칙 (가장 중요)

사용자가 과거에 가장 많이 겪은 문제 중 하나다.

1. **모든 장표는 이 발주처 고유의 사실 하나 이상에 연결한다.** 시스템 이름, 수치, 요구사항 번호, 발주처가 쓴 표현. 근거 필드가 비면 다시 쓴다.
2. **바꿔치기 테스트**: 발주처 이름만 바꿔 다른 사업 제안서에 넣어도 말이 되는 문장이면, 이 사업의 구체적 사실을 넣어 다시 쓴다.
   - 나쁨: "최신 기술 기반의 안정적 시스템을 구축합니다."
   - 좋음: "Hazelcast 3.12의 클러스터 비호환을 일괄 전환과 2회 리허설로 해소해 실시간 경매 중단 없이 Java 17로 전환합니다."
3. **효과와 수치는 근거와 함께.** 근거가 없으면 [근거 필요]. 회사 실적이 필요하면 [자산 필요: 무엇]. 지어내지 않는다.
4. **방법을 약속한다.** "최선을 다하겠습니다" 대신 무엇을 몇 번, 언제, 어떤 기준으로 하는지 쓴다.
5. **대안이 있으면 비교하고 권고안을 명시한다.** "A 또는 B를 검토"는 모호 표현으로 간주된다. 비교표로 보여 주고 "권고: A(근거)"로 끝낸다.

## 문체

- 헤드메시지는 합니다체 문장(발표 자료에서 가장 자연스럽다) 또는 사업 설정에서 정한 종결형을 따른다. 한 제안서 안에서는 통일한다.
- 본문은 개조식. 한 장에서 명사형과 "~함"을 섞지 않는다.
- 모호 표현 금지 목록은 `references/style-guide.md`.
- 용어는 `project.md`의 용어 목록(또는 용어사전)과 통일한다. 같은 대상을 장마다 다르게 부르지 않는다.

## 묶는 단위와 밀도 (사용자 확인 사항)

- 장표는 **메뉴·기능그룹 단위**로 묶는다(요구사항 10~20건 = 장표 1장). 요구사항마다 장표를 만들지 않는다.
- 본문 필드는 `01 …`, `02 …`처럼 **패널 단위**로 쓴다(패널 3~4개 + 하단 표·차트). PPT에서 R9 번호 패널이 된다.
- 요구사항 번호는 **본문에 쓰지 않고** `근거`·`대응` 필드에만 쓴다. **요구사항 대응표 장표는 만들지 않는다.**
- **밀도(1~5, 기본 3)에 맞춰 내용의 양을 정한다.** 밀도를 올리면 근거 있는 내용(세부 방법, 수치, 사례, 산출물, 효과)을 더해 패널·항목을 늘리고, 내리면 중요도가 낮은 내용부터 뺀다(밀도 5 ≈ 패널 4~5개·행 6~7, 밀도 1 ≈ 패널 2~3개·행 3). 기준표와 빼는 순서는 `visual-patterns.md` 7장. 더할 내용이 모자라면 지어내지 말고 [근거 필요]로 남긴다.

## 작성 순서와 분량

- 전략 단계에서 정한 **우선순위 순서**(배점 큰 장부터)로 쓴다.
- 장표 수는 전략 단계의 예상 장표 수를 기준으로 하되 ±20% 안에서 조정한다.
- 연속된 세 장표가 같은 도식 유형이면 하나를 다른 유형으로 바꾼다(PPT 단조로움 방지).

## 분담

- PM이 스킬로 전 장 초안을 만든다. 장마다 `담당` 필드를 채운다.
- 담당자가 파일을 고친 뒤 `/제안서 검수`로 일관성을 맞춘다.
- 특정 장만 다시 쓸 때(`/제안서 원고 3장`)는 `project.md`의 Win theme·용어·가정을 먼저 읽고, 다른 장과 수치(일정·인원·공수)가 어긋나지 않게 한다.

## 관문 C 보고

`python <스킬>/scripts/review_storyboard.py 제안작업`을 먼저 돌려서 결과를 함께 보여 준다.
- 장별 장표 수, 상태
- [근거 필요]·[자산 필요]·[가정] 개수와 위치
- 도식 없는 장표, 연속 동일 도식
- 추적대상 누락 수
- 결정 요청: 채워야 할 회사 자산 목록, 확인할 가정
