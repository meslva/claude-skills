# 도식 패턴 라이브러리

장표마다 **내용에 맞는 도식을 먼저 고른다.** 텍스트는 도식을 설명하는 보조다. 아래 패턴의 "구현"은 `scripts/deck.py`의 메서드 이름이다. 예시 코드는 `assets/example_build_deck.py`에 있고, 렌더링 결과를 보려면 그 파일을 실행한다.

## 목차
1. 고르는 법 (내용 → 패턴)
2. 패턴별 설명
3. AI스러운 장표 경고 신호
4. 디자이너 품질 기준
5. 샘플 장표에서 패턴 배우기
6. 회사 수주 제안서 패턴 (하우스 스타일 컴포넌트)

---

## 1. 고르는 법

| 장표가 말하려는 것 | 우선 고를 패턴 | 보조로 붙이기 좋은 것 |
|---|---|---|
| 지금 문제 → 바뀐 모습 | As-Is/To-Be `compare` | `callout`(핵심 변화 한 줄) |
| 시스템 구성·계층 | 계층 아키텍처 `layers` | 신규 요소 강조(`new: True`), 측면 패널(보안·운영) |
| 절차·흐름(누가 무엇을) | 스윔레인 `swimlane` | 결정점(`decision`), 강조 단계(`hl`) |
| 단계·방법론 | 단계 흐름 `process` | 아래 남는 공간에 `kpi_cards` 또는 `callout` |
| 일정·로드맵·컷오버 | 간트 `timeline` | 단계 띠(`bands`), 마일스톤, 오른쪽 `kpi_cards` |
| 대안 비교·권고 | 비교표 `table(highlight_col=권고안)` | 아래 `callout("권고: …")` |
| 성과·목표 수치 | 숫자 카드 `kpi_cards` | `chart`(추이), 출처 표기 |
| 추이·비중·비교 수치 | 네이티브 차트 `chart` | 옆에 해석 `bullets` 3줄 이내 |
| 전환·유입 구조 | 퍼널 `funnel` | 오른쪽 `chart` 또는 단계별 설명 |
| 위험 관리 | 리스크 매트릭스 `matrix` | 오른쪽 대응 `cards` |
| 조직·역할 | 조직도 `org` | 아래 R&R `table` |
| 병렬 전략·차별화 | 카드 그리드 `cards` | 번호·태그로 구분 |
| 체크포인트·절차 요약 | 세로 단계 `steps_vertical` | 오른쪽 도식(표·차트) |
| 요구사항 대응 | 대응 매핑 `table` | 요구 ID 열, 반영 장표 열 |
| 전략 체계(목표·전략·과제) | 기둥 매트릭스 `pillar_matrix` | 하단 `summary_bar` |
| 핵심 시스템과 주변 기능 | 허브 4사분면 `hub_quadrant` | 하단 `summary_bar` |
| 화면·기능 설명 | 화면 콜아웃 `screen_callout` | `stamp("예시")` |
| 결론·기대 효과 | 순환 링 `cycle_ring` | 하단 `kpi_strip` |
| 등급·우선순위 | 피라미드 `pyramid` | 옆 `table`(등급별 기준) |
| 원칙·기준 목록 | 라벨 행 `label_desc_rows` | `tab_panel`로 묶기 |
| 절차 요약(5단계 안팎) | 스텝 레일 `step_rail` | 위에 `compare` |
| 병렬 과제 3~4개 | 번호 카드 `numbered_cards` | 아이콘, 순서색 |

회사 수주 제안서 스타일의 조합 규칙(레시피)은 6장.

**한 컴포넌트가 영역을 다 채우지 못하면 빈 공간을 늘리지 말고 보조 도식을 붙인다.** `process`와 `org`는 사용한 아래쪽 y 좌표를 돌려준다. 그 아래에 `kpi_cards`, `callout`, `table`을 둔다.

## 2. 패턴별 설명

### 계층 아키텍처 — `layers`
- **언제**: 목표 시스템 구성, 기술 스택, 연계 구조.
- **구성**: 위에서 아래로 채널 → 서비스 → 기반 → 데이터. 오른쪽에 보안·운영 같은 공통 관리 패널.
- **좋은 예**: 이 사업의 실제 시스템 이름(오토벨, GAOS, CS 응찰)과 버전(Java 17, Tomcat 10)을 쓰고, 신규·변경 요소만 강조선으로 표시.
- **나쁜 예**: "Presentation / Business / Data" 같은 일반 명칭만 있는 계층. 어느 사업에나 들어간다.

### As-Is → To-Be — `compare`
- **언제**: 개선 전후, 현행 한계와 목표.
- **구성**: 왼쪽 회색(현행), 가운데 주황 화살표(변화 요약 한두 단어), 오른쪽 파랑(목표). 각 패널 위에 한 줄 요약(`sub`).
- **좋은 예**: 양쪽 항목이 1:1로 대응한다(현행 4개 ↔ 목표 4개). 목표 쪽 핵심어를 `**굵게**`로 강조.
- **나쁜 예**: 양쪽 항목이 서로 대응하지 않아 무엇이 바뀌는지 읽히지 않는다.

### 스윔레인 — `swimlane`
- **언제**: 여러 주체가 관여하는 업무 절차(가입 승인, 정산, 장애 대응).
- **구성**: 왼쪽 주체 이름, 칸 번호로 순서, 결정점은 마름모, 끝은 타원.
- **좋은 예**: 새로 생기는 단계(예: 전자서명 동의)를 `hl`로 강조하고 헤드메시지가 그 단계를 설명.

### 단계 흐름 — `process`
- **언제**: 방법론, 추진 단계, 전환 절차.
- **구성**: 쉐브론 머리(번호+단계명), 기간, 단계별 핵심 2~3개.
- **주의**: 단계마다 설명이 두세 줄뿐이면 상자가 짧게 끝난다. 아래에 숫자 카드나 핵심 메시지를 붙인다.

### 간트·로드맵 — `timeline`
- **언제**: 전체 일정, 단계별 오픈, 컷오버 계획, 인력 투입 기간.
- **구성**: 상단 단계 띠(1단계/2단계), 기간 머리, 행별 막대, 마일스톤(주황 마름모).
- **좋은 예**: 오픈·보고·리허설 같은 핵심 시점만 마일스톤으로. 막대 안 글자는 짧게.

### 비교표 — `table`
- **언제**: 대안 비교, 요구사항 대응, R&R, 인력 투입표.
- **구성**: 권고안 열을 `highlight_col`로 강조, 첫 열은 비교 기준.
- **좋은 예**: 표 아래 `callout`으로 "권고: A안 — 근거"를 명시. 대안을 나열만 하면 모호 표현으로 간주된다.

### 숫자 카드 — `kpi_cards`
- **언제**: 목표 수치, 핵심 성과, 규모 요약.
- **좋은 예**: 숫자는 크게, 설명은 짧게, 출처나 [가정]을 주석으로. 카드는 2~4개.
- **나쁜 예**: 근거 없는 수치. 반드시 `source`나 [가정] 표시.

### 네이티브 차트 — `chart`
- **언제**: 추이(선), 항목 비교(막대), 구성비(도넛), 누적(누적 막대).
- **구성**: 데이터 레이블 표시, 값 축 숨김(깔끔), 단일 계열이면 범례 숨김, 제목에 단위.
- 편집 가능한 차트로 남기므로 담당자가 PPT에서 숫자를 고칠 수 있다.

### 퍼널 — `funnel`
- **언제**: 가입 → 전환 → 참여 같은 단계별 감소 구조.
- **구성**: 위가 가장 넓다. 오른쪽에 단계 설명.

### 리스크 매트릭스 — `matrix`
- **언제**: 위험 관리, 이슈 우선순위.
- **구성**: 가로 발생 가능성, 세로 영향도, 칸에 리스크 이름. 오른쪽에 상위 리스크 대응 카드.

### 조직도 — `org`
- **언제**: 수행 조직, 협업 체계.
- **구성**: PM 상단, 팀별 상자, 측면 점선(발주처·PMO). 아래에 핵심 역할 R&R 표.

### 카드 그리드 — `cards`
- **언제**: 차별화 포인트, 전략 과제, 대응 방안 묶음.
- **구성**: 번호 배지, 제목, 핵심 2~3개, 태그(대응 리스크·요구 ID).

### 복잡 도식 — `image`
- 네이티브 도형으로 표현하기 어려운 것(네트워크 구성도, 복잡한 데이터 흐름)만 이미지로 넣는다.
- matplotlib 등으로 그린 경우 원본 스크립트와 SVG를 `05_PPT/_도식원본/`에 저장해 수정할 수 있게 한다.

## 3. AI스러운 장표 경고 신호

아래가 보이면 다시 만든다.
- 제목 + 불릿만 있는 장표가 연속 두 장 이상.
- 같은 크기 사각형 3~4개에 문장을 넣어 나열한 장표가 반복된다.
- 상자 안 문장이 세 줄을 넘는다.
- 모든 요소가 같은 색·같은 굵기라 시선이 갈 곳이 없다.
- 도식이 내용을 증명하지 않고 장식으로만 있다(예: 의미 없는 원형 배치).
- 한 컴포넌트가 영역을 늘려 채워서 상자 안 아래쪽이 텅 비었다.
- 연속 세 장표가 같은 도식 유형이다.
- 헤드메시지가 제목을 반복할 뿐 주장이 없다.

## 4. 디자이너 품질 기준

- **한 장표 한 메시지.** 헤드메시지가 주장, 도식이 증거, 본문은 보충.
- **시선 흐름**: 헤드메시지 → 핵심 도식 → 보조 설명. 왼쪽 위에서 오른쪽 아래로.
- **강조색은 한두 곳.** 기본은 남색·파랑, 주황은 핵심 변화·권고·마일스톤에만.
- **숫자는 크게.** 성과 수치는 카드로 뽑아 26~32pt.
- **글자 크기**: 회사 가이드 기준(`company-guide.md` 2장). 본문 10~8pt, 강조 13pt까지, 주석 7~8pt. deck.py 메서드에 주는 `size`에는 `text_scale`(0.75)이 곱해진다(size 11 → 8pt).
- **정렬과 여백**: 컴포넌트 사이 0.15~0.25인치. `hsplit`·`vsplit`로 격자를 맞춘다.
- **출처 표기**: 수치·주장에는 `content_slide(source=...)`로 근거를 단다.
- **레이아웃 다양성**: 장 안에서 패턴을 섞는다. 같은 패턴이 연속되면 하나를 바꾼다.

## 5. 샘플 장표에서 패턴 배우기

사용자가 이전 수주 제안서나 좋은 장표 샘플을 주면:
1. `render_pptx.ps1`로 장표 이미지를 만든다(PDF면 페이지 이미지).
2. 장표마다 기록한다: 말하려는 것, 도식 유형, 레이아웃 분할(예: 좌 60 우 40), 색 사용, 글자 크기, 특징적 장치(번호 배지, 단계 띠, 강조선 등).
3. 이 파일 2장에 "사례" 항목으로 추가하고, `deck.py`에 없는 패턴이 반복되면 새 메서드로 만든다.
4. 회사 템플릿의 색·글꼴이 드러나면 `project.md`의 브랜드 설정에 반영한다.

## 6. 회사 수주 제안서 패턴 (하우스 스타일 컴포넌트)

자사 수주 제안서(양부대 스마트물류)와 컨소시엄 수주 제안서(NH 싱씽몰)를 장표 단위로 분석해 얻은 패턴이다. **"AI스럽다"와 "디자이너 품질"을 가른 차이는 도형 종류가 아니라 조합과 밀도였다.**

| AI스러운 장표 | 수주 제안서 장표 |
|---|---|
| 컴포넌트 하나가 본문 전체를 채움 | 주 도식 + 보조 블록 + 하단 요약 바 |
| 11~14pt 큰 글자, 항목 3~4개 | 7~9pt, 항목 많음, 영역마다 제목 라벨 |
| 아이콘 없음 | 도식의 대상(사람·시스템·건물 등)을 나타내는 아이콘(장식용 남발 금지 — 8장) |
| 모든 상자 같은 색 | 순서색 01~04, 탭 라벨, 점선 구분 |
| 제목 + 불릿 | 헤드메시지 → 슬로건 → 영문 키워드 → 도식 → 결론 바 |
| 가정 화면을 실물처럼 | 예시·Sample·Illustrative 도장 |

**아이콘 사용 규칙(사용자 확정)**: 원본·도식에 사람·건물·화면·경보 같은 아이콘이 필요하면 **`assets/icons/` 라이브러리에서 실제 아이콘을 끌어다 쓴다.** 빈 원·회색 박스 같은 자리표시로 대체하지 않는다.
- 색인(`assets/icons/index.md`) 키워드로 후보를 찾고 **PNG를 직접 열어 모양을 확인**한 뒤 번호(`iNNN`)로 지정한다(키워드 첫 일치에 맡기지 않는다 — 없는 키워드면 `d.icon`이 빈 원을 그린다).
- 한 장표 안에서는 한 스타일 묶음만(본문 기본 A 남색·컬러 라인 i218~i479).
- 빌드 스크립트에서는 없는 번호면 실패하는 래퍼를 쓴다(빈 원이 몰래 들어가지 않게). 맞는 아이콘이 없으면 `[자산 필요: 아이콘 – 무엇]`으로 표시한다.

### 6.1 장표 레시피

본문 영역 `a = d.area()`를 아래처럼 나눈다(비율은 출발점).

| 레시피 | 분할 | 쓰는 곳 |
|---|---|---|
| **R1 전략 기둥** | `vsplit(a, [0.8, 0.2])` → `pillar_matrix` + `summary_bar` | 추진 전략, 목표 체계 |
| **R2 일정+기준** | `vsplit(a, [0.16, 0.84])` → `kpi_strip` / `hsplit(body, [0.68, 0.32])` → `tab_panel`+`timeline`, `tab_panel`+`label_desc_rows` | 전환·컷오버, 오픈 계획 |
| **R3 전후+절차** | `vsplit(a, [0.68, 0.32])` → `compare` + `step_rail` | 개선 과제, 통합·이관 |
| **R4 허브** | `vsplit(a, [0.8, 0.2])` → `hub_quadrant` + `summary_bar` | 목표 시스템, 서비스 구성 |
| **R5 화면 설명** | `screen_callout(a, …)` (화면 캡처가 있으면 `image=`) + 도장 | UI/UX, 관리자 화면, 기능 설명 |
| **R6 등급+절차+표** | `hsplit(a, [0.5, 0.5])` → 왼 `tab_panel`+`pyramid` / 오른 `vsplit` → `numbered_cards` + `table` | 장애·품질·보안 등급 |
| **R7 결론 링** | `vsplit(a, [0.82, 0.18])` → `cycle_ring` + `kpi_strip` | 장 결론, 기대 효과 |
| **R9 번호 패널 (기본형)** | `vsplit(a, [0.55~0.6, 나머지])` → 위 `hsplit` 3~4칸 `panel("01 제목")` + `item_rows`/`icon_rows`, 아래 `sub_title("04 …")` + `table`·`chart`·`step_rail`·`summary_bar` | **상세 구축 방안 기본형.** 메뉴·기능 묶음 단위 장표(양부대 '업무보고 및 산출물' 형식) |

## 7. 밀도 옵션 (1 ~ 5, 기본 3)

밀도는 **본문 영역의 빈 공간을 내용으로 채우는 정도**다. 네 가지 원칙을 지킨다.

1. **필수·원본 내용은 밀도와 무관하게 빠짐없이 모두 담는다(최우선).** 요구사항(RFP) 내용, 참조 제안서(재활용 원본)의 해당 장표 내용은 밀도가 낮든 높든 전부 포함한다. 원본에 표가 9행이면 9행, 법령 이름이 길면 그대로 — **줄이거나 생략하지 않는다.** 자리가 부족하면 배치·간격부터 조정하고, 데이터가 너무 많을 때만 그 블록 글자를 8pt까지 줄인다. 8pt에서도 안 되면 문구를 다듬거나 장을 나눈다(8pt 미만 금지). 사용자가 "중요도는 판단해도 된다"고 하면 뺄 수 있지만, 뺀 항목은 모두 보고한다.
2. **밀도를 올린다 = 원본을 다 담고도 남는 빈 공간에만 근거 있는 내용을 더한다.** 추가분(알파)은 RFP·원고·회사 자료에 실제로 있는 내용이어야 한다. **추가 방법**: 기존 내용과 구성은 그대로 두고, 박스 크기·간격을 줄여 공간을 만든 뒤 그 공간에 **별도 블록**으로 넣는다. 기존 목록에 섞어 넣거나 레이아웃을 새로 만들지 않는다. 기존 자료에 없던 **새 업무·약속**(예: "○○ 책임자 지정")은 RFP에 있더라도 만들어 넣지 않는다.
3. **이미 내용으로 가득 찬 장표에는 더 추가하지 않는다.** 밀도가 높아도 빈 공간이 없으면 그대로 둔다. 채움은 목적이 아니라 결과다. **판단 기준: 알파를 넣은 뒤에도 모든 구역이 여백 기준(표 행 0.14인치, 칸 0.14인치)을 지킬 때만 넣는다.** 박스를 줄여 자리를 만들 때도 이 여백 아래로 줄이지 않는다. 원본만으로 적당히 찬 장표에 알파를 억지로 넣으면, 원본 구역까지 빽빽해져 "억지로 끼워 넣은" 장표가 된다(사용자 지적 2026-11-03 — 3.7에 보호조치 표를 더했다가 장 전체가 빽빽해져 빼고 원본만 남김).
4. **자리를 만들려고 기존·필수 내용을 삭제하지 않고, 기존 글자를 줄이지도 않는다.** 알파를 넣으려고 원본 내용을 지우거나 원본 글자를 작게 하는 것은 금지. 원본 크기로 공간이 안 남으면 알파를 넣지 않는다.
5. **구역 균형.** 장표 안 모든 구역(표·카드·도식)이 비슷한 밀도로 보여야 한다. 위에서부터 고정 크기로 쌓고 남은 자리를 마지막 구역에 몰아주면, 위는 헐렁하고 아래(대개 추가한 표·블록)는 빽빽해져 "억지로 끼워 넣은" 장표가 된다. 순서: ① 표·목록에 필요한 높이를 먼저 계산(표 행 = 줄 수 × 글자 크기 × 1.2 + 위아래 여백 0.14인치 이상, `Deck.row_heights()`) → ② 도식·카드는 필요한 만큼만(내용보다 0.5인치 이상 비는 칸 금지) → ③ 남는 공간은 모든 구역에 고르게 나눈다. 그래도 표 여백이 0.14인치에 못 미치면 도식을 더 줄이고, 그래도 안 되면 알파를 줄이거나 뺀다(장 전체가 고르게 촘촘한 것은 괜찮다). `verify_pptx.py`의 "빽빽한표"로 점검한다.

기본 글자 크기: 사업 템플릿이 본문 크기를 정했으면 그것을 따른다(예: 템플릿 본문 10pt → `text_scale` 1.0). 템플릿이 없으면 회사 가이드 기본(`text_scale` 0.75, 본문 ≈ 8pt, `min_size` 8pt). 원본 내용이 넘칠 때만 줄인다(하한 8pt, 순서는 `05-ppt.md` 6번). `Deck(..., density=4)` 또는 `brand["density"]`로 주고, 사용자는 `/제안서 ppt 밀도=4`처럼 부른다. **기본은 3.** 예전 표기 상/중/하는 4/3/2로 읽는다.

|---|---|---|---|---|
| **5** 최대 | 3에 세부 방법·수치·사례·산출물·리스크 대응까지 더함. 실측 기준(A4 가로 장표 1장): 글자 약 1,900자, 도형 약 200개(그림·아이콘 25개 안팎), 본문 세로 95%·면적 85% 채움 — 밀도 3의 약 2배 | 95% 이상 | 패널 4~5개 + 행 6~7, 타일 12개, 보조 블록 2개 + 요약 바 | 요구사항이 많은 상세 구축 방안, 전체 아키텍처처럼 한 장에 다 넣어야 할 때 |
| **4** 높음 | 3에 세부 방법·수치·근거를 더함 | 90% 이상 | 패널 4개 + 행 5~6, 타일 10개, 보조 블록 1~2개 | 제출용 본책 |
| **3** 보통(기본) | 핵심 메시지 + 방법 + 근거 + 기대효과. 실측 기준(A4 가로 장표 1장): 글자 약 900자, 도형 약 70개, 본문 세로 80%·면적 65% 채움 | 80% 이상 | 패널 3~4개 + 행 4~5, 타일 8개, 보조 블록 1개 | 일반 본문 |
| **2** 낮음 | 3에서 부연·중복·보조 블록을 뺌 | 75% 이상 | 패널 3개 + 행 3~4, 타일 6개 | 요약 장표 |
| **1** 최소 | 핵심 메시지와 결정적 근거만 남김 | 65% 이상 | 패널 2~3개 + 행 3, 타일 4~5개, 큰 숫자·도식 위주 | 발표용, 간지 성격의 장표 |

- **본문 채움 목표**: 헤드메시지·슬로건 아래 본문 영역에서 도형·글자가 차지하는 세로 범위의 비율이다. 렌더링 이미지에서 맨 아래 블록 끝과 본문 영역 바닥 사이 빈 띠, 블록 사이 큰 빈칸을 보고 판단한다. **빈 공간이 있을 때만** 내용을 더해 채운다 — 원고·RFP·회사 자료에 있는 세부 항목, 수치, 사례, 보조 블록(요약 바, 근거 칩, 기대효과 띠). **이미 원본 내용으로 가득 차 목표를 넘겼으면 더 넣지 않는다**(채움은 결과이지 목적이 아니다). 자리가 없다고 **원본·필수 내용을 지우고 다른 걸 넣지 않는다.** 글자를 키우거나 도형만 늘려 빈 공간을 메우지 않는다. **없는 내용을 지어내서 채우지 않는다** — 더할 근거가 없으면 [근거 필요]로 알린다.
- **밀도를 내릴 때 빼는 순서**: ① 같은 말을 되풀이한 문장·항목 ② 어느 사업에나 맞는 일반론 ③ 부연 설명·예시 ④ 보조 블록(근거 칩, 기대효과 띠) ⑤ 세부 수치(핵심 수치 하나만 남김). 핵심 메시지, 요구사항 대응 내용, 결정적 근거는 빼지 않는다.
- **밀도와 원고**: 원고 단계에서 밀도가 정해져 있으면 패널·항목 수를 위 표에 맞춰 쓴다. 밀도 5인데 원고 항목이 적으면 장을 합치는 쪽을 먼저 검토한다.
- **글자 크기**: 밀도를 올려도 글자를 줄여 자리를 만들지 않는다. 원본(필수) 내용이 넘칠 때만 배치 조정 → 해당 블록 글자 축소(하한 8pt) → 문구 다듬기·장 나누기 순으로 맞춘다. 알파(추가 내용) 때문에 넘치면 알파를 줄인다.
- **같은 원고로 밀도만 바꿔** 제출용(4~5)과 발표용(1~2)을 따로 만들 수 있다.

빌드 스크립트에서 개수를 밀도에 맞추는 도우미:

```python
d = Deck(TEMPLATE, BRAND, PROTO, density=4)
rows = d.pick(7, 6, 5, 4, 3)   # 밀도 5→7줄, 4→6, 3→5, 2→4, 1→3 (높은 밀도부터 적는다)
rows = d.pick(6, 4, 3)         # 예전 방식(상·중·하)도 된다: 5·4→6, 3→4, 2·1→3
d.item_rows(s, inner, items[:rows], size=9)
d.feature_row(s, lane, [{"icon": "i402", "title": "관리 기능", "bullets": d.cut(bullets)}])  # 5·4 전부 / 3 최대 5 / 2 최대 4 / 1 최대 3
d.density, d.fill              # 현재 밀도(1~5), 채움 목표 비율
```

- `d.cut(목록)`은 목록의 앞쪽부터 남기므로, 원고에서 항목을 **중요한 순서로** 적어 둔다.


## 8. 장표 품질 규칙 (전 사업 공통 — 사용자 지적을 모은 것)

PPT·시안을 만들거나 고칠 때마다 지킨다. 사업마다 다른 값(템플릿 색, 표 스타일, 원본 쟁점 결정)은 `project.md`에 둔다.

**구성**
- **원본의 내용(글·숫자·항목)은 지키고, 배치는 자유롭게 다시 설계한다.** 사용자 지적(2026-11-05): "원본의 내용을 바꾸지 말라는 것이지 배치를 바꾸지 말라는 말이 아니야." 다시 정하는 것은 읽는 방향, 행·열 격자, 위치, 상자·글자 크기, 선 경로, 가로→세로 재구성이다. 원본 좌표를 비율만 바꿔 옮기거나, 자동 배치(Mermaid 등)에 맡겨 이미지로 넣지 않는다. 두 방식 모두 "못 만들었다"는 평가를 받았다. 정렬이 삐뚤어진 것("90년대 같다·빼뚤빼뚤하다")도 배치를 다시 짜면서 함께 바로잡는다.
- **도식을 다시 그리는 순서.** ① 덱의 역할별 글자 크기를 정한다. ② 읽는 방향을 정한다(세로 판형이면 핵심 흐름을 위→아래 한 열로 세우고 갈래는 옆 열로). ③ 행·열 격자와 열 머리글을 정한다. ④ 선의 뜻을 정한다(색 2가지 이하 + 범례 한 줄). ⑤ 입력·출력을 위·아래 띠로 두고 각 상자를 연결되는 열에 맞춘다. ⑥ 그 뒤 상자를 놓고 선 경로를 정한다. 선은 열 사이 빈 칸으로 돌리고, 머리글이나 상자 글자를 가로지르지 않게 한다. 기준 예시는 사용자가 직접 만든 `MES_소개서/M2M_MES_소개서_v7.pptx` 14쪽이다.
- **정리용 문구는 넣어도 된다(2026-11-05 허락).** 열·행 머리글과, 선·색의 뜻을 알리는 범례 한 줄은 원본에 없어도 넣고, 보고할 때 목록으로 알린다. 기능 코드를 빼거나 항목 이름을 바꾸는 것처럼 원래 글이 바뀌는 일은 시안과 함께 먼저 묻는다. 그 밖의 추가(장식 번호, 요약 띠, 아이콘, 머리 띠 문구)는 여전히 하지 않는다.
- **장표 제목과 내용이 일치해야 한다.** 본문을 2~3개 번호 구역으로 나누면 각 구역 제목이 절 제목에 직접 대응해야 한다(예: "관계 법령 및 지침 준수" → ① 관련 법령 ② ○○법에 따른 준수 사항 ③ ○○기준에 따른 보호조치).
- **새 업무·약속을 만들지 않는다.** 기존 장표·회사 자료·참고 제안서에 없던 일(책임자 지정 등)은 RFP에 있어도 수행 내용으로 쓰지 않는다. 참고 제안서에서 가져온 문구는 출처(파일·쪽)를 빌드 코드 주석에 남기고, 다른 회사 이름·시스템명·수치는 일반 표현으로 바꾼다.
- **"다른 제안서 스타일로" = 레이아웃 방식만 참고한다.** 그 제안서의 판형·로고·디자인을 복사하지 않는다. 사업 템플릿과 판형(세로면 세로)을 유지한다.

**디자인**
- **색은 템플릿이 정한 팔레트만** 쓴다(마스터 바깥에 둔 색 견본 등). 배경과 글자의 대비가 너무 강한 조합(진한 면에 흰 글씨 남발)을 피한다.
- **경보색(오렌지·빨강)은 진짜 경고에만** 쓴다(결함 등급, 리스크, 데드라인 경고). 분류색(차수·신규 구분), 순서 번호·콜아웃 표식, 장식에 쓰면 진짜 강조가 묻힌다. 경보가 아닌 강조는 팔레트 안의 차분한 색 하나(틸·청회색 계열 등)로 통일한다. 쓸 색은 샘플 2~3안을 보여 주고 사용자가 고르게 한다.
- **볼드는 구역 제목(소제목)에만.** 본문·표·라벨에 볼드를 남발하지 않는다.
- **원본의 띠·패널·원형 같은 디자인 조각은 이미지로 넣지 않고 도형으로 그린다.** 그림은 아이콘·실제 화면 캡처·차트·기관 로고만. 표를 이미지로 넣지 않는다.
- **정렬**: 모든 열·칸을 본문 영역 격자에 맞춘다. 겹침·삐뚤어짐, 한두 글자만 다음 줄로 넘어가는 줄바꿈이 없게 한다.

**아이콘**
- **아이콘을 장식으로 쓰지 않는다**(사용자 지적 2026-11-03: "아이콘을 무차별적으로 사용"). 표 첫 열·카드 머리·띠·라벨마다 아이콘을 붙이지 않는다. 장표당 개수 목표도 두지 않는다.
- 쓰는 곳은 도식에서 대상(사람·조직·시스템·건물·화면)을 나타내 글자보다 빨리 읽히게 할 때, 또는 원본 장표에 있던 아이콘을 살릴 때뿐이다. 애매하면 넣지 않는다.

**글자**
- **흐름 도형(셰브런·오각 화살표) 라벨은 번호와 이름을 한 줄에 같은 크기로** 넣는다(`d.step_label()`). 두 줄 라벨은 PowerPoint 화면에서 도형을 넘친다. 한 줄(행)에 놓인 라벨은 모두 같은 크기로 맞춘다. 칸에 안 들어가면 이름을 줄이거나 번호를 도형 밖으로 뺀다.
- **한 글상자 안에서 글자 크기를 섞지 않는다.** 예외는 일부러 강조한 핵심 문구와 카드 제목뿐이다(`verify_pptx.py`의 "크기혼용"으로 확인).
- **줄 간격은 고정 pt(글자 크기 × 1.2)**로 둔다(`Deck.save()`가 자동 적용, `BRAND["line_pt"]`). 배수 간격은 PDF로 렌더링한 확인 화면보다 PowerPoint 화면에서 줄이 약 1.3배 커져, 확인 때 맞던 글자가 사용자 화면에서 넘친다.
- **글자 크기는 원본이 아니라 덱 전체의 체계에 맞춘다**(사용자 지적 2026-11-05). 같은 역할의 글(제목·소제목·상자 이름·본문·참고)은 다른 장과 같은 크기로 한다. 기존 덱에 장을 더할 때는 그 덱의 역할별 크기를 먼저 실측하고(`디자인.md`), 크기를 정한 뒤 배치를 거기에 맞춘다. 배치에 맞추다 글자가 작아지면 글자가 아니라 배치를 다시 짠다. 하한은 8pt이고, 템플릿이 참고 문구·코드에 더 작은 크기를 쓰면 그 크기까지 허용한다. 글자를 줄여 빈 공간을 메우거나 자리를 만들지 않는다.

**작업 방식**
- **샘플 먼저**: 스타일·구성을 바꾸는 작업은 한두 장 샘플로 확인받은 뒤 전체에 적용한다.
- **덮어쓰기 전**: 같은 폴더의 `~$<파일명>` 잠금 파일(PowerPoint·Excel이 열고 있음)을 확인하고, 기존 파일은 백업 이름으로 남긴다. 사용자가 파일을 열어 둔 채면 "저장하지 말고 닫은 뒤 다시 열라"고 알린다.
- **검증 후 제시**: `verify_pptx.py` 완료 조건 0(남긴 것은 사유와 함께) + 렌더링을 직접 보고 난 뒤에만 결과를 보여 준다.
