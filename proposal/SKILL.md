# 기술 제안서 작성 (/제안서)

RFP를 받아 **분석 → 질의 → 전략·목차 → 장표 원고 → PPT → 검수**까지 수행한다. 여러 사업에 반복해서 쓰는 범용 스킬이다. 사업마다 달라지는 정보는 작업 폴더의 `project.md` 한 곳에 모은다.

이번 호출의 인자: `$ARGUMENTS`

## 이 스킬이 특히 막아야 하는 세 가지 문제

사용자가 과거 제안서 작업에서 겪은 문제다. 모든 단계에서 이것을 기준으로 판단한다.

1. **AI가 만든 티가 나는 PPT.** 사각형 도형에 글자만 얹은 장표가 반복됐다. 목표는 디자이너가 손본 것 같은 장표다. 장표마다 내용에 맞는 도식을 먼저 고르고, 텍스트는 도식을 보조한다. → `references/05-ppt.md`, `references/visual-patterns.md`
2. **뻔한 일반론.** 어느 사업에나 넣을 수 있는 문장으로는 점수를 받지 못한다. 모든 장표를 이 발주처의 고유한 사실(시스템 이름, 수치, 요구사항 번호, 발주처가 쓴 표현)에 연결한다. → `references/04-storyboard.md`
3. **마감 압박으로 떨어지는 완성도.** 역산 일정, 배점 큰 장 우선 작성, 장별 완성도 점검표로 뒤쪽 장이 대충 채워지는 것을 막는다. → `references/06-review.md`

## 호출될 때마다 먼저 할 일

1. **작업 폴더 찾기.** 현재 작업 디렉터리에서 `제안작업/project.md`를 찾는다. 없으면 착수 단계부터 시작한다.
2. **`project.md` 읽기.** 사업 정보, 확정된 전략, 관문 승인 상태, 용어, 담당자가 들어 있다. 모든 판단은 이 파일에 맞춘다. 여러 담당자가 같은 폴더에서 스킬을 불러도 같은 전략과 톤으로 쓰게 하는 장치다.
3. **인자 해석.** 아래 표에 따라 단계를 정한다. 인자가 없거나 `상태`이면 진행 상황을 짧게 보고하고 다음에 할 일을 제안한다.
4. **해당 단계의 참고 파일을 읽고** 수행한다. 끝나면 `project.md`의 진행 상태를 갱신한다.

| 인자 | 단계 | 참고 파일 |
|---|---|---|
| `착수` (또는 첫 호출) | 0. 사업 설정 파일·역산 일정표 | `references/00-kickoff.md` |
| `분석` | 1. RFP·요구사항 분석 → **관문 A** | `references/01-analysis.md` |
| `질의` | 2. 질의서(발송용·내부관리·설명회) | `references/02-questions.md` |
| `전략` | 3. Win theme·차별화·가정·목차·배점 배분 → **관문 B** | `references/03-strategy.md` |
| `원고`, `원고 2장` | 4. 장표별 원고(스토리보드) → **관문 C** | `references/04-storyboard.md` |
| `ppt`, `ppt 2장`, `ppt 밀도=4` | 5. PPT 제작·렌더링 확인(밀도 1~5, 기본 3) | `references/05-ppt.md`, `references/visual-patterns.md` |
| `테마 <템플릿> [대상 PPT]` | 템플릿(PPTX·PDF)의 스타일(색·글꼴)을 입힌다. 구조·틀·배치는 그대로. 대상 PPT가 있으면 그 PPT를 새 파일로 바꾸고, 없으면 새 PPT용 브랜드 설정을 만든다 | `references/07-theme.md` |
| `검수` | 6. 추적표·모호 표현·일관성·완성도 → **관문 D** | `references/06-review.md` |
| `일정` | 역산 일정 재계산 | `references/00-kickoff.md` |

**밀도**는 **본문 영역의 빈 공간을 내용으로 채우는 정도**를 1~5로 정한다(기본 3). 핵심: ① **필수·원본 내용(요구사항, 재활용 원본 제안서의 해당 내용)은 밀도와 무관하게 빠짐없이 모두 담는다.** ② 밀도를 올린다는 것은 **원본을 다 담고도 남는 빈 공간에만** 근거 있는 내용을 **별도 블록으로** 더하는 것이다 — 기존 내용·구성은 그대로 두고 박스 크기·간격을 줄여 공간을 만든 뒤 넣는다. 기존 목록에 섞지 않는다. ③ **이미 가득 찬 장표에는 추가하지 않는다**(채움은 결과이지 목적이 아니다). ④ **자리를 만들려고 기존·필수 내용을 삭제하지 않고, 기존 글자를 줄이지도 않는다**(하한 8pt). 원본 크기로 공간이 안 남으면 추가하지 않는다. ⑤ **구역 균형**: 내용을 더한 뒤에도 장표 안 모든 구역이 비슷한 밀도로 보여야 한다. 위 구역은 헐렁하고 마지막 구역(추가한 표·블록)만 빽빽하면 "억지로 끼워 넣은" 장표다 — 표 행 여백 0.14인치 이상, 남는 공간은 모든 구역에 고르게 나눈다. `ppt`뿐 아니라 시안·단일 장표 제작, 원고의 항목 수에도 같은 값을 쓴다. 기준은 `references/visual-patterns.md` 7장·8장.

사용자가 자연어로 범위를 좁혀 요청하면(예: "플랫폼 경매 장만 다시", "질의서에 이 항목 추가") 그 요청을 따르되, 앞 단계 산출물이 없으면 무엇이 빠졌는지 알리고 필요한 최소 분석만 먼저 한다.

## 관문에서는 멈춘다

| 관문 | 시점 | 보여 줄 것 |
|---|---|---|
| A | 분석 완료 | 핵심 요약, 발견한 불일치·리스크 상위 항목, 결정이 필요한 점 |
| B | 전략·목차 완료 | Win theme, 차별화 포인트, 가정 목록, 목차와 배점별 분량 |
| C | 원고 완료 | 장별 요약, [근거 필요]·[자산 필요]·[가정] 개수, 텍스트 장표 비율 |
| D | 검수 완료 | 추적표 누락, 모호 표현, 불일치, 완성도 점검표 |

관문에서는 **무엇을 만들었고, 무엇이 가정이며, 무엇을 결정해 달라는지**를 짧게 보여 주고 사용자의 승인을 기다린다. 승인은 `project.md`에 날짜와 함께 기록한다. 방향이 틀린 채로 원고와 PPT까지 가면 되돌리는 비용이 가장 크기 때문에 관문을 건너뛰지 않는다. 사용자가 명시적으로 "관문 없이 끝까지"라고 하면 그렇게 하되 모든 가정을 [가정]으로 표시한다.

## 자기 검증 루프(완료 조건)

산출물을 만들거나 고친 뒤에는 **완료 조건을 숫자로 검사하고, 통과할 때까지 고치고 다시 검사한다.** 통과하기 전에는 "완료"라고 보고하지 않는다. 최대 5회 반복하고, 그래도 남은 것은 장 번호와 함께 "남은 문제"로, 잴 수 없었던 것은 "검증 못 함"으로 따로 보고한다.

| 작업 | 검사 | 완료 조건 |
|---|---|---|
| 원고 | `review_storyboard.py` | 추적표 누락 0, 모호 표현 0(남기면 사유), 수치 불일치 0 |
| PPT 새로 만들기 | `verify_pptx.py <pptx>` | 넘침·이탈·겹침·8pt 미만·튀는 색·빽빽한 표·두 줄 라벨 모두 0. "크기혼용"은 의도한 강조인지 확인 |
| 기존 PPT 고치기(테마·수정) | `verify_pptx.py <결과> --base <원본> [--plan …] [--redesigned …]` | **새로 생긴** 문제 0, 미적용 0. 원본에도 있던 문제는 보고만 |

- **튀는 색 방지**: 한 요소의 색이 장표 시각 비중(면적 × 색의 진하기 × 배경과의 대비)의 50% 이상을 차지하거나, 강한 색 면적이 장표의 30% 이상이거나, 강조색 계열이 4개 이상이면 미통과다. 색이 너무 튀면 그 영역만 눈에 들어오고 다른 영역이 읽히지 않는다. 고칠 때는 면적을 줄이거나 연한 색·테두리로 바꾸고, 강조색 계열을 줄인다.
- **요청 범위 점검**: 사용자가 바꾸라고 한 항목마다 "바뀐 곳 / 안 바뀐 곳"을 확인한다. 장표 XML만 보지 말고 레이아웃·마스터·테마·배경 그림·차트까지 본다.
- **숫자 검사 다음에 눈으로 본다**: 렌더링 이미지로 넘침·겹침·튀는 색·빈 공간을 다시 본다(윈도우 `render_pptx.ps1`, 맥 `render_pptx_mac.py`). 사용자가 PowerPoint로 작업 중이면 렌더링 전에 묻는다.
- 검사 도구가 잡은 문제가 실제로는 문제가 아니면(의도한 겹침 등) 그 사유를 보고에 적는다. 기준을 몰래 느슨하게 하지 않는다.
- **검사를 돌리기 전에 결과를 말하지 않는다.** "0건"은 실제 출력으로 확인한 뒤에만 보고한다.
- **장표 품질 규칙(전 사업 공통)**은 `references/visual-patterns.md` 8장에 있다. 사용자가 PPT 작업에서 지적한 내용을 모은 것이므로, PPT·시안을 만들거나 고칠 때마다 먼저 읽는다.

## 작업 폴더 구조

사업 폴더(세션을 연 폴더, 예: `C:\workFISH\글로비즈\`) 바로 아래에 `제안작업/`을 만든다. RFP가 하위 폴더(`1. RFP 원본\` 등)에 있어도 그 안에 만들지 않는다. 사업 폴더에 이미 분석·질의 산출물이 있으면 `01_분석/`·`02_질의/`에 복사하지 않고 `project.md`에 경로만 적어 그대로 쓴다.

```
제안작업/
  project.md                 사업 설정·전략·진행 상태 (assets/project-template.md 복사)
  00_일정/역산일정.md
  01_분석/  분석보고서.md, 요구사항매트릭스.xlsx, 용어사전.md, _추출/(텍스트·페이지 이미지)
  02_질의/  질의서.xlsx
  03_전략/  전략_목차.md, 추적대상.csv
  04_원고/  00_전체구성.md, 1장_*.md, 2장_*.md …
  05_PPT/   build_deck.py, 제안서_vN.pptx, _render/(장표 이미지), _도식원본/
  06_검수/  검수보고서.md, 완성도점검표.md
  자산/     회사 자료(받은 것)
```

## 핵심 원칙

- **사실과 판단을 구분한다.** 분석 문서에서 [사실]·[해석]·[가정]·[질의]를 표시한다. 섞이면 근거 없는 주장이 제안서까지 흘러간다.
- **지어내지 않는다.** 회사 실적, 인력 경력, 효과 수치를 만들어 내지 않는다. RFP는 허위 기재에 책임을 묻는다. 근거가 없으면 [근거 필요], 회사 자료가 없으면 [자산 필요: 무엇]으로 남기고 작업은 계속한다.
- **모호한 표현을 쓰지 않는다.** 한국 공공·대기업 평가에서 "~할 수 있다", "~가능하다", "~고려하겠다"는 흔히 "불가능"으로 간주된다. 약속은 단정형으로 쓴다. 목록은 `references/style-guide.md`.
- **요구사항 누락은 0점이다.** RFP의 필수 목차, 평가 항목, 요구사항을 추적 대상으로 등록하고 장표와 연결한다.
- **문서 간 불일치를 찾는다.** 본문과 간트, 본문과 엑셀, 구성도와 요구사항의 어긋남은 질의서와 리스크의 원천이다.
- **제안서는 설계가 아니다.** 사소한 기술 확인·결정을 하나씩 묻거나 문제 목록을 계속 늘리지 않는다. 불확실한 세부는 합리적 기본안(권장안)으로 쓰고 [가정]·[질의]로 표시한 뒤 넘어간다. 사용자에게는 범위·공수·일정·전체 방향을 바꾸는 큰 결정만 묻는다.

## 수정 요청을 다룰 때

기존 원고·PPT를 고치는 요청에서 사용자가 반복해 지적한 내용이다.

- **연속 지시는 직전 결과 안에서 수행한다.** 명령이 이어지면 다음 명령의 대상은 바로 앞 명령이 바꾼 문구·도형·장·파일이다. 문서 전체로 넓히지 않고, 범위 밖에서 같은 패턴을 발견해도 고치거나 정리를 제안하지 않는다. 범위가 애매하면 직전 결과 범위로 해석한다.
- **"○○라는 말은 필요 없다" = 그 표현만 뺀다.** 문장·줄·문단을 통째로 지우거나 다른 문구로 갈아 끼우지 않는다. 조사만 맞춰 asis/tobe로 보여 준다(예: "비운영 시간 1회 일괄 진행" → "비운영 시간에 진행"). 대상은 내가 고쳐 넣은 문구 안의 그 표현뿐이고, 원래 문서에 있던 같은 단어까지 찾아 지우지 않는다.
- **들어가면 안 될 내용은 지우지 말고 같은 자리에서 바꾼다.** 내부 메모("확인 필요", "질의 필요", 주의 박스)나 약점을 드러내는 문장이 보여도 도형 삭제부터 하지 않는다. 같은 자리에 줄 수·글자 수가 비슷한 문구로 바꾸는 안을 먼저 보여 주고 합의한다. 위험을 적은 문장은 대응 약속으로 바꾼다(예: "~ 가능성" → "~ 선확보"). 지우면 디자인이 깨진다.
- **기존 장표를 전면 개편하지 않는다.** 사용자가 만든 레이아웃·흐름을 뜯어고치는 재디자인은 요청이 없으면 제안하지 않는다.
- **결과 파일은 새 번호로 저장한다.** 기존 PPT를 고치거나 샘플을 만들면 원본이 어느 폴더에 있든 `05_PPT/{원본 파일명}_001.pptx`, 다음은 `_002`처럼 새 파일로 저장한다. 저장 전에 가장 큰 번호를 확인해 +1 한다. 원본을 제자리에서 덮어쓰지 않고, PPT를 `06_검수/` 등 다른 폴더에 두지 않는다.

## 말투와 문체

- 사용자와의 대화는 **존댓말**(~습니다/~입니다)로 한다.
- 산출물 문서는 문서체로 쓴다. 분석 보고서·용어사전은 하다체, 제안서 원고는 **헤드메시지는 완결된 주장 문장, 본문은 개조식**이다.
- "쉽게 말하면:" 같은 상투적 머리말을 쓰지 않는다. 사용자가 매우 싫어한다.
- 사용자에게 설명할 때는 쉬운 말을 쓰고, 전문용어는 처음 나올 때 짧게 풀이한다.
- 자세한 규칙은 `references/style-guide.md`.

## 회사 공통 폴더와 회사 규칙

회사 공통 자료는 **`C:\workFISH\제안공통\`**에 있다(다른 경로면 `project.md`의 "공용 자산 폴더"가 우선).

| 하위 폴더 | 내용 | 쓰는 곳 |
|---|---|---|
| `0. 참조. 탬플릿 공통 가이드\` | 회사 제안서 공통 가이드(상세, 서식 중심) | 문체·구성·서식 규칙 → `references/company-guide.md`에 정리되어 있다 |
| `1. 수주 제안서\` | 이전 수주 제안서(PPTX) | 도식 패턴·헤드메시지 사례 → `references/visual-patterns.md` 6장 |
| (없으면 요청) 회사자료 | 회사 소개·실적·인력·재무 | 5장 제안업체 일반, 차별화 근거 |

- **규칙 우선순위: 발주처 RFP > 회사 공통 가이드(`company-guide.md`) > 이 스킬의 기본 규칙.** 충돌하면 앞의 것을 따른다.
- **사업 폴더에 `디자인.md`가 있으면 PPT·도식 작업 전에 먼저 읽는다.** 템플릿 실측값(판형·작업 영역·색·글꼴 크기)과 회사 가이드 규칙을 합친 그 사업의 디자인 기준서다. 없으면 템플릿을 실측해 만들어 둔다.
- **PPT 템플릿 찾는 순서**: ① 사업 폴더의 템플릿(예: `글로비즈\0. 탬플릿\*.pptx`) ② `project.md`에 적힌 경로 ③ 회사 기본 템플릿(현재 없음) ④ 없으면 회사 가이드 서식을 반영한 기본 디자인. 템플릿이 있으면 원형 장표 복제 방식으로 만든다(`references/05-ppt.md`).
- 회사 자료가 정리되어 있지 않을 수 있다. 착수 단계에서 필요한 목록을 요청하고, 받은 자료는 `제안작업/자산/`에 둔다. 처리 방법은 `references/company-assets.md`.
- 공통 폴더에 새 가이드나 수주 제안서가 추가되면, 사용자가 요청할 때 다시 분석해 `company-guide.md`·`visual-patterns.md`를 갱신한다.

## 스크립트

스크립트 경로는 이 스킬 폴더 기준이다. 실행 전 `python` 또는 `powershell`로 호출한다. 필요한 Python 패키지는 시스템 Python에 설치하지 않는다(`--break-system-packages` 금지). 사업 폴더의 기존 가상환경을 쓰고, 없으면 사업 폴더에 `.venv`를 만들어 설치한 뒤 `.venv/bin/python`(윈도우 `.venv\Scripts\python`)으로 실행한다.

| 스크립트 | 용도 |
|---|---|
| `scripts/extract_inputs.py <입력파일/폴더> <출력폴더>` | PDF 텍스트 추출 + 글자가 적은 페이지 이미지 렌더링, 엑셀 시트 덤프·내장 이미지 추출, Word 텍스트 추출 |
| `scripts/review_storyboard.py <제안작업 폴더> [--owner B]` | 원고 검수: 추적표, 모호 표현, 태그 집계, 텍스트 장표 탐지, 수치 대조. `--owner`는 담당별 검수(원고 `담당` 필드·추적대상 `담당` 열 기준) |
| `scripts/deck.py` | PPT 도식 컴포넌트 라이브러리(python-pptx). `build_deck.py`에서 import 해서 쓴다 |
| `scripts/render_pptx.ps1 -Path <pptx> -OutDir <폴더>` | PowerPoint로 장표를 PNG로 렌더링해 눈으로 확인 |
| `scripts/render_pptx_mac.py <pptx> <폴더> [--slides 3,5]` | 맥용 렌더링. 확인할 장만 남긴 사본을 고유 이름으로 열고 그 이름으로만 닫는다 |
| `scripts/verify_pptx.py <pptx> [--base 원본] [--plan plan.json]` | 완료 조건 검사: 넘침·이탈·겹침·8pt 미만·튀는 색·빽빽한 표(행 여백 0.14in 미만)·두 줄 흐름 라벨, 원본 대비 새로 생긴 문제·미적용. 확인용: 한 글상자 안 글자 크기 혼용 |
| `scripts/reskin.py analyze\|apply\|brand …` | 테마(스타일) 적용: 색·글꼴 대응표(asis/tobe) 작성 → 기존 PPT에 적용(새 파일), 새 PPT용 BRAND 추천. 템플릿은 PPTX·PDF |
